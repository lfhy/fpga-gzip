# gzip 四核吞吐优化（2026-11-02）

本轮在已验证的 250 MHz gzip 固件上继续减少主机复制、启动等待和 DMA 供数空档。
所有吞吐单位均为十进制 GB/s，按四核完整输入字节数除以整组事务的墙钟时间计算。

[原始数据与参数](gzip-throughput-20261102.json)保留所有对照行，包括降低吞吐的试验。
原固件构建为 `86950339975258`，已上板验证的 32 KiB 输入预取构建为
`24138492833269`。以下将主机路径对照与固件对照分别列出。

## 已验证的输入预取固件

在每条 512 位 XDMA H2C 总线与 512→64 位转换器之间加入 32 KiB BRAM FIFO，
四路共增加 36 个 BRAM36。在主机完成、映射和重启下一个 DMA 请求时，队列
继续给压缩核供数；每核软复位同时清空该 FIFO 与输入宽度转换器。
压缩核仍是 8 lane、8 KiB 块、250 MHz 的 gzip 编码器。

同一 benchmark、默认有界输出、H2C/EOP 均为 1 MiB、四核、每组 4 GiB，
每种输入三轮的中位数：

| 输入 | 分块 / Go P | 原固件 GB/s | 输入预取 GB/s | 提升 |
| --- | --- | ---: | ---: | ---: |
| 混合 | 256 MiB / 16 | 7.364 | 7.602 | 3.24% |
| 文本 | 256 MiB / 16 | 7.494 | 7.748 | 3.38% |
| 随机 | 256 MiB / 16 | 7.061 | 7.024 | -0.52% |
| Silesia 全部 12 文件拼接 | 1 GiB / 8 | 7.394 | 7.620 | 3.06% |

所有输出均完整解压比较。文本中位数达到端口理论值 8 GB/s 的 96.84%。
随机数据未获益，不能宣称所有输入都提速。新镜像通过 720 组板上边界与
数据模式验证，默认输出与显式直接输出各 360 组；setup WNS 为 0.002 ns、
hold WHS 为 0.010 ns，内部未约束端点和 DRC 错误均为 0。

新 bitstream SHA256：
`b27a75067ed8e4f98a93c4976d0d698e78cd58763acbd001a8a488537981fc47`。
构建脚本、RTL 与仿真见 [固件源码](../firmware/multialgo/README.md)。

另以每核单个 10 GiB member、四核共 40 GiB、16 个 P、EOP 1 MiB 重复三轮，
文本中位数 7.695 GB/s（7.645–7.770），混合数据 7.559 GB/s（7.522–7.562）。
六组输出全部完整解压比较，覆盖 64 位输入计数与 gzip ISIZE 的 32 位回绕。
EOP 2 MiB、256 MiB 分块的随机数据另完成一组 96 GiB 长测，达到 7.192 GB/s。

## 已采用的主机改动

- EOP gzip 写入 `*bytes.Buffer` 且显式设置 `Options.DirectOutput` 时，C2H 直接填充剩余容量，再提交 Buffer 长度；
  省去中间缓冲、输出复制及独立写入 goroutine。普通 Writer 保留有界流水线。
- 保留 gzip 头、CRC32、ISIZE、EOS、输入输出计数与最终状态校验。每次 DMA 前
  重新取得可用容量；剩余容量足够容纳较小的末次请求时，避免扩大整个 Buffer。
- 软复位和启动先立即读取最多八次状态，再使用原有带超时的休眠轮询；
  避免正常约 1 微秒的板上复位被主机定时器拉长。
- 默认 H2C 分片改为 1 MiB，限制每次页映射和重新启动的开销。
- benchmark 显式转发固件身份，算法不匹配在任何 RESET/DMA 前拒绝；
  新增 `-buffered-output` 对照和压缩窗口内进程 CPU 时间。

相同固件、同一 benchmark、四核、8 个 P、每组 4 GiB 输入，轮换测试顺序，
每种配置三轮。以下为中位数：

| 输入 / 分块 | 原输出路径、快速复位 | 直接输出、旧复位 | 直接输出、快速复位 |
| --- | ---: | ---: | ---: |
| 混合 / 4 MiB | 5.924 | 5.862 | 6.226 |
| 混合 / 64 MiB | 7.275 | 7.234 | 7.281 |
| 文本 / 4 MiB | 6.273 | 5.960 | 6.319 |
| 文本 / 64 MiB | 7.361 | 7.375 | 7.402 |
| 随机 / 4 MiB | 5.263 | 5.111 | 5.659 |
| 随机 / 64 MiB | 6.895 | 6.895 | 6.951 |

64 MiB 随机数据直接输出的进程 CPU 用时从 1.216 秒降至 0.612 秒；
混合数据从 0.829 秒降至 0.540 秒。CPU 时间为 Linux `RUSAGE_SELF`
的 user + system，测量区间与压缩计时相同，不含事后解压、不含其他进程、
中断或内核工作线程的用时。不能把它当作整机 CPU 用量。

## 长测否决直接输出作为默认值

同一旧固件、256 MiB 分块、16 个 P、每组 96 GiB，直接输出的混合数据仅
5.005 GB/s、随机数据 3.664 GB/s；文本输出很小，仍为 7.408 GB/s。
恢复有界缓冲复制后，混合、文本、随机分别为 7.287、7.424、7.048 GB/s。
直接输出的混合/随机中断分别为 481,092/839,256 次，缓冲路径为 188,289/261,132 次。
这与大量分散输出页导致更多 C2H EOP 描述符和中断的路径一致；本镜像只有一个 MSI 向量。
因此直接输出保留为显式选项，默认继续复用少量固定 DMA 缓冲区。
短测的 CPU 收益不能替代长期吞吐验证。

## 8 GB/s 的含义

四个 64 位、250 MHz 端口每拍连续传输的总上限是
`4 × 8 × 250,000,000 = 8,000,000,000 B/s`。
现有 HLS 的块切换、流水线填充与排空、DMA 请求间隔都占用真实时间。

用已验证的原 HLS RTL，在输入持续有效、输出持续就绪条件下仿真：

| 输入 | 单核输入阶段 | 单核完整事务 | 说明 |
| --- | ---: | ---: | --- |
| 文本 1 MiB | 1.964891 | 1.861369 | 输入阶段乘四约 7.860；完整时间包含排空 |
| 混合 4 MiB | 1.939193 | 1.908893 | 输入阶段乘四约 7.757 |
| 文本 8 MiB | 1.975959 | 1.962238 | 完整事务乘四约 7.849 |
| 随机 8 MiB | 1.889679 | 1.873404 | 完整事务乘四约 7.494 |

这些是单核仿真的阶段计数，不能冒充四核上板结果；仿真输出也完整解压比较。
8 MiB 随机仿真采用独立的 Python 固定种子数据，SHA256 与生成器写入 JSON，
与 Go 板测随机序列不同。
随机数据在当前固定 Huffman 实现中增大约 5.53%，64 位输出端口限制其理想输入
吞吐至约 `8 / 1.0553 = 7.58 GB/s`。要使这类数据也接近 8 GB/s，后续需要
增加 DEFLATE stored-block 选择或拓宽输出，单纯加大主机缓冲不足以突破该限制。

## 未采用的参数与驱动试验

所有试验均完整解码并逐字节比较；原始结果保留在 JSON 中。以下改变未观察到
足够稳定的收益，最终未更改安装的驱动或 PCIe 配置：

- H2C 也合并物理连续页的 SG；保留页固定、映射和清理。
- 单个同步 H2C 请求在中断中直接完成，省去一次工作队列；以及与 SG 合并的组合。
- PCIe MRRS 从 512 调到 1024、2048、4096；DMA 配置寄存器确认接受变化，但吞吐没有稳定改善。
- H2C 4/16/64 MiB、C2H 4/16 MiB、BAR mmap 和更多 Go P 的对照。

最终 MRRS 512、MPS 256，驱动参数与本轮开始时相同。试验模块均从独立副本编译，
安装模块文件与原驱动源码未改动。96 GiB 对照的内核日志未发现 DMA 超时或失败，
直接输出测试出现 2330 条旧驱动的 idle-service 通知，原始日志一并保留。

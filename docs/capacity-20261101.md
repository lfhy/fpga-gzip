# 四核持续压缩与 EOP DMA 优化（2026-11-01）

本轮目标是测量并提高四核合计的实际压缩吞吐。所有 `GB/s` 均为十进制，
按完整输入字节数除以四核整组事务的墙钟时间计算。

## 最终持续测试

新 EOP 固件配合五个驱动补丁，四核、压缩阶段 8 个 Go P、64 MiB chunk，
每轮连续压缩 **96 GiB（103,079,215,104 字节）**。约 50% 可压缩输入的三轮结果：

| 轮次 | 压缩时间 | 吞吐 | XDMA 中断数 |
| --- | ---: | ---: | ---: |
| 1 | 14.141899818 s | **7.289 GB/s** | 176,912 |
| 2 | 14.143705305 s | **7.288 GB/s** | 151,251 |
| 3 | 14.138102260 s | **7.291 GB/s** | 164,210 |

每轮每核 384 次，共 1,536 份 gzip 输出，全部由标准库 gzip 解压并逐字节比较。
三轮均超过 6 GB/s，中位数为 **7.289 GB/s**；存储比例约 53.64%。
相同条件下，每种另测一轮 96 GiB：

| 输入 | 压缩时间 | 吞吐 | 输出/输入 | XDMA 中断数 |
| --- | ---: | ---: | ---: | ---: |
| 确定性随机 | 14.756413175 s | **6.985 GB/s** | 105.53% | 200,922 |
| 重复文本 | 13.940025905 s | **7.394 GB/s** | 2.778% | 101,799 |

随机输入依然逐字节经过 FPGA，即使 gzip 比原文大，也没有用 raw 模式替代。
五轮共 480 GiB，所有输出校验通过；内核监测日志没有 DMA 等待超时或失败。
这是直接压缩 RAM 数据的四核合计吞吐，compactfs 的实际文件读写单独记录。
[机器可读报告](capacity-20261101.json)保存原始行、参数、构建信息和文件 SHA256。
原始报告位于本机 `/data1/fpga-sixgb-20261101-133035`，最终五轮文件前缀为
`seg1m-sustained-`。新固件和报告另归档于
`/root/FPGA-4IP/qz01_compress_4ip/validated/20261101-eop`。
固件通过易失 JTAG 装载，重启掉电后需要按归档说明重新装载。

## 测试口径

- 使用 `examples/benchmark-capacity`，直接调用 FPGA pipeline，不启用压缩预测、
  原数据跳过、内容去重或 CPU 回退。
- 输入、输出位于 RAM。输出空间在计时前分配并逐页触碰；计时包含输入 CRC32、
  所有 H2C/C2H、寄存器访问、设备打开关闭及最终状态检查。
- 每核和每次迭代都写入不同的 8 字节标签。所有 gzip 输出均保留，计时结束后
  完整解压并比对原文，通过后才发布该行结果。
- 数据生成、预分配和最终完整解压不计入压缩吞吐。这是主机与板卡的压缩指标；
  compactfs 的 NVMe 缓存和 backend 指标另行测量。
- `core_operations` 中的纳秒数是各操作的累计墙钟时间，包含阻塞等待，不能当作
  CPU 时间，也不能把四核数值相加后当成整组耗时。

三类输入：`text` 为固定行文本；`random` 为确定性随机数据；`fixture` 为 fio
生成的约 50% 可压缩数据，解码后 4 MiB 的 SHA256 为
`d378f587d40daec3d80194bf95ba89d3b8851097cd5adc538ebff7955f5b77a1`。
大 chunk 重复该 fixture；板卡 gzip 的最终存储比例约为 53.64%。

## 本轮实现

SDK 对 `bytes.Reader` / `bytes.Buffer` 借用输入分片，省去输入环形缓冲的一次复制；
其他 Reader 仍走有界缓冲。输入 CRC 和精确长度检查保留，超出声明长度的后缀不会被消耗。
DMA 缓冲只在事务的所有阶段结束后复用，总缓存受数量和字节上限约束。

新 shell 的 C2H packetizer 可以在 gzip 最终 TLAST 提前结束主机请求，主机因此可以
先提交 1 MiB 读取。原协议必须先等待足够 `OUT_BYTES`，再提交精确长度读取。
SDK 通过每核 `0x40` 的 `0x475a0001` 标识协商；收到短包时仍要求 EOS 和精确计数。
主机协议与验证方法见 [EOP 指导](../firmware/qz01-eop/README.md)。
板级 RTL、派生补丁、781 个 shell 仿真用例及整卡构建脚本保存在私有固件工程。

只读 mmap 输入还修复了 XDMA 的 H2C 页权限。旧驱动在 DMA 提交前会返回 EFAULT，
此前 compactfs 曾因此全部回退 CPU；这类结果没有计入 FPGA 性能。
SDK 仅对零字节 EFAULT 复制并重试一次，驱动补丁让 H2C 直接固定可读页。
安装与回滚见[驱动指导](driver-install.md)。

BAR mmap 保持可选，默认关闭。库不改变宿主的 `GOMAXPROCS`。

## EOP 协议与驱动对照

新固件的正式静态时序裕量为 WNS **+0.005727 ns**、WHS **+0.004895 ns**，
全部 371,718 个需布线网络已布通，bitstream 生成前 DRC 为 0 errors。
占用 LUT 91.43%、BRAM 90.42%、URAM 100%。本轮通过易失 JTAG 装载，未写 Flash。
bitstream SHA256：`5fa1a1997ca935d9e4730bd5e427617af52fdecc7b3622cdccf6d9bc3c20758e`。

只把读取扩大到 1 MiB，会触发官方 EOP 路径的逐 SG 段完成通知和重复扫描。
驱动补丁使用内核 SG helper 在 DMA 段长度限制内合并物理连续页，只作用于
streaming C2H 的 EOP 读取。原协议和 H2C 的 SG 布局保持原样。

相同新固件、四核、8 个 Go P、CPU `8-23,56-71`、每核 1 GiB、1 MiB 请求，
每行均完整解压比较通过：

| 输入 / chunk | EOP 原 SG 布局 | EOP 连续页合并 | 中断数：原布局 → 合并 |
| --- | ---: | ---: | ---: |
| fio 50% / 4 MiB | 1.932 GB/s | 5.913 GB/s | 106,388 → 39,791 |
| fio 50% / 64 MiB | 2.280 GB/s | 7.232 GB/s | 92,647 → 39,124 |
| 文本 / 4 MiB | 5.924 GB/s | 6.017 GB/s | 32,448 → 6,886 |
| 文本 / 64 MiB | 6.972 GB/s | 7.337 GB/s | 32,207 → 6,506 |
| 随机 / 4 MiB | 1.412 GB/s | 5.344 GB/s | 139,494 → 71,491 |
| 随机 / 64 MiB | 1.629 GB/s | 6.902 GB/s | 120,927 → 69,925 |

这是参数和驱动对照用的短测；持续结果单独记录。大包使 50% / 64 MiB 的整组
C2H 读取降到 2,240 次。两个 EOP 对照都为这个数量，收益来自 SG 路径的改变。
原始文件：`eop-base.json`、`eop-sg.json`，均位于本轮 `/data1` 目录。
只安装新固件、保留原 SG 布局不是推荐的性能配置。

这个短测阶段的驱动 `srcversion` 为 `94DCC95A2173C02F0AD9552`，`poll_mode=0`，
保持正常 Go 抢占。四核真实板卡 456 个边界用例在各阶段分别通过。

## 持续测试发现的描述符链尾问题

96 GiB 长测复现了短测不易遇到的 10 秒停顿。首次两轮吞吐为 2.884 和
4.985 GB/s，全部解压比较通过；第三轮加入隔离 ftrace 诊断，捕获到一次
`xdma_xfer_submit` 耗时 10.035 秒。页映射阶段只有数微秒。

临时诊断记录到 C2H 的额外链等待超时：`rv=0 state=SUBMITTED desc=0/10`。
根因是一个用户读取可能在描述符环回绕处拆成多条链：末包落在前一条链的最后
一个描述符时，官方整链完成分支没有设置 EOP，继续提交后续链。packetizer
已经结束本次请求，后续链收不到数据，10 秒超时后驱动返回先前收到的完整末包。

第四个驱动补丁在整链完成时也检查 EOP，在提交多余链前结束读取；保持真实
DMA 超时与错误检查。512 GiB 定向诊断命中 4 次这个链尾边界，修复后没有超过
1 秒的等待。这项诊断将输出送到 `io.Discard`，只用于检查控制路径，未计入
压缩性能结果。正式模块不包含诊断字段和日志，`srcversion` 为
`E3CDCD760B1013A292DE373`；安装的模块 SHA256 为
`d49da1a6ed95f2b3a125380b3ecab6eafab21517751349dbbdfa63b1cf5fb770`。
四个补丁按安装文档顺序应用，已核对能逐字节重建安装模块的修改源文件。

后续长测采用正式模块并重新做完整解压比对。压缩阶段仍固定 8 个 Go P；
计时后的解压验证显式使用 24 个 P，每个验证 worker 持有独立期望输入和标签，
不修改压缩输入。验证完成后恢复原 P 数，错误时也恢复。测试覆盖串核、内容错误、
截断尾部和长度错误；所有数据通过完整标准 gzip 解码和逐字节比较后才发布结果。

## DMA 段长度与最终持续配置

EOP 连续页合并后，设备仍使用默认 64 KiB DMA 段上限。第四个补丁解决了链尾
10 秒停顿，但三轮 96 GiB / 50% 数据仍为 6.425、3.988、6.405 GB/s；内核日志
未再出现该超时。保留这些原始数据，没有将较慢一轮排除后称为稳定结果。

第五个补丁将 XDMA 设备声明的 DMA 段上限至少提高到 1 MiB，允许内核在物理连续
的页上生成更少描述符，不跨过物理不连续处。原先的页固定、DMA 映射和清理仍保留，
卸载与 probe 失败时恢复原上限。28 位硬件描述符可以承载这一长度。

使用相同新固件、参数和短测方法，五补丁模块的结果：

| 输入 | 4 MiB chunk | 64 MiB chunk | 64 MiB 中断数：64 KiB 段 → 1 MiB 段 |
| --- | ---: | ---: | ---: |
| fio 50% | 5.831 GB/s | 7.204 GB/s | 39,124 → 7,877 |
| 文本 | 6.003 GB/s | 7.311 GB/s | 6,506 → 4,782 |
| 随机 | 5.284 GB/s | 6.874 GB/s | 69,925 → 10,989 |

短测吞吐接近原有上限，持续测试则使用此配置重新独立启动进程测量。
正式模块 `srcversion` 为 `EE98305A8E92F08D1564207`，SHA256 为
`eae1164fed42284844faca2a01ba967640aaa9c89ee6169a9040b6c6bd35d476`。
五个补丁按驱动文档顺序应用，已逐字节核对能够从固定官方版本重建受测修改源文件。
最终配置使用 `poll_mode=0`、正常 Go 抢占、H2C 4 × 1 MiB、EOP C2H 1 MiB；
BAR mmap 默认关闭。主机 CPU 固定 `8-23,56-71`，XDMA IRQ 请求 CPU 集合为 `0-23,48-71`；最终安装后的有效 CPU 为 3。

## 长 member、协议与服务验证

每核单次输入 **10 GiB**，四核合计 40 GiB，计时 **5.785903484 s**，
吞吐 **7.423 GB/s**；四份完整 gzip 均解压并逐字节比较通过。
这另外覆盖了单个 gzip member 超过 4 GiB 时的 64 位输入/输出计数和 ISIZE 回绕，
不是只累计很多小 member 的输入量。

- 最终五补丁驱动：四核 zero/text/random、1 字节至约 1 MiB 的边界，共 456 例通过。
- 新固件强制 `-legacy`：4 MiB 和 64 MiB chunk 各压缩 2 GiB，完整解压比较通过。
- 四核 Unix HTTP daemon：32 个不同的 4 MiB 请求全部解压比较通过，success=32、
  failure/busy=0。这是功能验证，HTTP 与 Python 解压耗时不用于压缩吞吐。
- RTL packetizer 781 例及旧边界仿真通过，静态时序、DRC 与布线报告见固件归档。
- SDK 的 `CGO_ENABLED=0 go test ./...`、`go vet ./...` 和基准验证器的 race 检查通过；
  race 仅用于测试，产品构建使用 `CGO_ENABLED=0`。

## compactfs 完整链路复测

本轮三次各写入 10 GiB，cache、metadata 与本地 backend 均在 `/data1` 同一 NVMe，
4 MiB chunk、8 个后台任务、四核独立算法 worker（8 P / 4 并发），Deflate 预测保留。
每轮 2,560 次实际 FPGA 编码和新 backend 对象提交，预测跳过、CPU 回退及错误均为 0。

| 中位数 | MiB/s |
| --- | ---: |
| fio 前台写入，local fsync | 1,652 |
| 写入进程开始至 backend 排空 | 1,557 |
| raw 热缓存读取 | 6,619 |
| 空 compactfs cache，从 backend 解压读取 | 647 |

含排空结果约 **1.633 GB/s**，不能与上面的 7.29 GB/s RAM 压缩相混。
每轮完整 raw 热读与 backend 解压读均通过 fio CRC32C，backend 读取与解码各 2,560 次；
Linux page cache 保留，没有把这项读测试称为物理盘冷读。解压仍由 CPU 完成。
原始报告为 `compactfs-fpga-4tnht_qu/results.json`，完整条件另见 compactfs 的
`docs/benchmark-fpga-capacity-20261101.md`。

这轮没有观察到文件系统吞吐随压缩吞吐同比提高。最终写回排空通常只需数毫秒；
前台 raw cache、元数据与编码对象持久化仍在同一完整链路内，本轮没有将其余耗时
单独归因到某个硬盘或 CPU 阶段。正式 compactfs 依赖仍为已发布 v0.0.2，
独立 worker 通过临时 modfile 构建本地新版 SDK。

## 内存基准复现

```bash
CGO_ENABLED=0 GOWORK=off go build -o /tmp/fpga-capacity ./examples/benchmark-capacity
# 本机 FPGA 位于 NUMA 0；其他机器先按自己的拓扑调整这两组 CPU。
fpga_gzip_irq=$(cat /sys/bus/pci/devices/0000:39:00.0/irq)
printf '%s\n' '0-23,48-71' | sudo tee "/proc/irq/$fpga_gzip_irq/smp_affinity_list" >/dev/null
taskset -c 8-23,56-71 /tmp/fpga-capacity \
  -patterns=text -sizes-mib=64 -cores=4 -procs=8 -verify-procs=24 \
  -per-core-mib=24576 -rounds=1 -h2c-mib=1 -slots=4 \
  -packet-kib=1024 -output=/data1/capacity-text.json
```

96 GiB 测试会预分配约 108 GiB 输出内存，需要足够 RAM；短测试可将
`-per-core-mib` 改为 `1024`。CPU 集合对应本机 FPGA 所在的 NUMA 0，
其他机器需按其拓扑调整。`-legacy` 强制原读取协议，`-mmap` 显式开启 BAR 映射。
JSON 记录完整参数、输入 SHA256、协议、请求大小、实际 P 数、DMA 操作及中断增量。

约 50% 数据使用 `-patterns=fixture -source=/path/to/fixture.gz`。
本机原始 fixture 路径可从
`/data1/compactfs-optimize-20261031-yo_olxa2/decoder-cpu-fixture.txt` 读取。
使用新生成的 fio fixture 时应记录其 SHA256，并以相同 fixture 做前后对照。

本轮在已验证的 250 MHz gzip 固件上继续减少主机复制、启动等待和 DMA 供数空档。
所有吞吐单位均为十进制 GB/s，按四核完整输入字节数除以整组事务的墙钟时间计算。

[原始数据与参数](gzip-throughput-20261102.json)保留所有对照行，包括降低吞吐的试验。
原固件构建为 `86950339975258`，已上板验证的 32 KiB 输入预取构建为

## 推荐组合：输入预取与 H2C 描述符合并

连续的页，减少 DMA 描述符。仍使用原来的页固定、DMA 映射、等待与清理路径，
合并长度受 DMA segment 上限约束。补丁与重建步骤见[驱动指导](driver-install.md)。

同一固件、四核、256 MiB 分块、16 个 P、H2C/EOP 均为 1 MiB、每组 4 GiB，

## 已采用的主机改动

- EOP gzip 写入 `*bytes.Buffer` 且显式设置 `Options.DirectOutput` 时，C2H 直接填充剩余容量，再提交 Buffer 长度；
  省去中间缓冲、输出复制及独立写入 goroutine。普通 Writer 保留有界流水线。
- 保留 gzip 头、CRC32、ISIZE、EOS、输入输出计数与最终状态校验。每次 DMA 前
  重新取得可用容量；剩余容量足够容纳较小的末次请求时，避免扩大整个 Buffer。
- 软复位和启动先立即读取最多八次状态，再使用原有带超时的休眠轮询；
  避免正常约 1 微秒的板上复位被主机定时器拉长。
- 默认 H2C 分片改为 1 MiB，限制每次页映射和重新启动的开销。
- benchmark 显式转发固件身份，算法不匹配在任何 RESET/DMA 前拒绝；
  新增 `-buffered-output` 对照和压缩窗口内进程 CPU 时间。

相同固件、同一 benchmark、四核、8 个 P、每组 4 GiB 输入，轮换测试顺序，
每种配置三轮。以下为中位数：

| 混合 / 64 MiB | 7.275 | 7.234 | 7.281 |
| 文本 / 4 MiB | 6.273 | 5.960 | 6.319 |
| 文本 / 64 MiB | 7.361 | 7.375 | 7.402 |
| 随机 / 4 MiB | 5.263 | 5.111 | 5.659 |
| 随机 / 64 MiB | 6.895 | 6.895 | 6.951 |

同一旧固件、256 MiB 分块、16 个 P、每组 96 GiB，直接输出的混合数据仅

## 8 GB/s 的含义

四个 64 位、250 MHz 端口每拍连续传输的总上限是
`4 × 8 × 250,000,000 = 8,000,000,000 B/s`。
现有 HLS 的块切换、流水线填充与排空、DMA 请求间隔都占用真实时间。

用已验证的原 HLS RTL，在输入持续有效、输出持续就绪条件下仿真：

| 输入 | 单核输入阶段 | 单核完整事务 | 说明 |
| --- | ---: | ---: | --- |
| 文本 1 MiB | 1.964891 | 1.861369 | 输入阶段乘四约 7.860；完整时间包含排空 |
| 混合 4 MiB | 1.939193 | 1.908893 | 输入阶段乘四约 7.757 |
| 文本 8 MiB | 1.975959 | 1.962238 | 完整事务乘四约 7.849 |
| 随机 8 MiB | 1.889679 | 1.873404 | 完整事务乘四约 7.494 |

这些是单核仿真的阶段计数，不能冒充四核上板结果；仿真输出也完整解压比较。
8 MiB 随机仿真采用独立的 Python 固定种子数据，SHA256 与生成器写入 JSON，
与 Go 板测随机序列不同。
随机数据在当前固定 Huffman 实现中增大约 5.53%，64 位输出端口限制其理想输入
吞吐至约 `8 / 1.0553 = 7.58 GB/s`。要使这类数据也接近 8 GB/s，后续需要
增加 DEFLATE stored-block 选择或拓宽输出，单纯加大主机缓冲不足以突破该限制。

```sh
  -cores=4 -procs=16 -verify-procs=24 -patterns=text \

  -h2c-mib=1 -slots=4 -packet-kib=1024 -output=/data1/gzip-members.json
```

这些 CPU 集合适用于本机 NUMA 拓扑。benchmark 的输入和 gzip 输出在内存中，
只将小型 JSON 报告写到 `/data1`；`-verify-procs` 只影响计时后的完整解压比较。
混合数据另传 `-patterns=fixture -source=输入样本.gz`；Silesia 将全部 12 文件按
字典序拼接后封装为 gzip 输入，并使用 `-sizes-mib=1024 -procs=8`。
各次实际命令、样本 SHA256、输出大小、逐轮耗时和验证结果均保存在原始 JSON。

## 未采用的参数与驱动试验

所有试验均完整解码并逐字节比较；原始结果保留在 JSON 中。以下改变未观察到
足够稳定的收益，因此未采用：

- 单个同步 H2C 请求在中断中直接完成，省去一次工作队列；以及与 SG 合并的组合。
- PCIe MRRS 从 512 调到 1024、2048、4096；DMA 配置寄存器确认接受变化，但吞吐没有稳定改善。
- H2C 4/16/64 MiB、C2H 4/16 MiB、BAR mmap 和更多 Go P 的对照。

H2C SG 合并在旧固件、64 MiB 分块的早期测试中未见稳定收益；之后在输入预取固件、
256 MiB 分块下，原驱动前后夹测确认了上表收益，因此作为第六补丁采用。
这两个条件同时改变，不能仅凭这些结果断定收益完全来自某一种交互机制。

最终 MRRS 512、MPS 256，驱动参数与本轮开始时相同。试验模块均从独立副本编译，
原驱动源码保持原样，归档另存六补丁源码、模块及五补丁回滚模块。
96 GiB 对照的内核日志未发现 DMA 超时或失败，
直接输出测试出现 2330 条旧驱动的 idle-service 通知，原始日志一并保留。
